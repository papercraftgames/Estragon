# UI-01 — native focus and keyboard ownership

[Issue #197](https://github.com/papercraftgames/Estragon/issues/197) supplies the shared foundation for Checkbox/UI-02 and Input/UI-03. UI-02 Checkbox and UI-03 [Input/String binding](INPUT.md) reuse it; the text prototype below records the original UI-01 decision.

## One native focus owner

Godot's `Viewport.gui_get_focus_owner()` is authoritative. A runtime-only, transparent internal Control beneath each Estragon Button/Toggle/Checkbox is its native keyboard endpoint; it owns no layout or drawing and ignores mouse picking. The Node2D still owns its measured border-box, appearance, pointer hit testing and `pressed`/`value_changed` signals. The endpoint has exactly that arranged size, inherits native transforms/visibility/clipping/Viewport, and never moves the user control to an overlay tree. This is an actual native focus endpoint, not reconciliation bookkeeping or an alternate focus state.

Button/Toggle/Checkbox expose native-shaped `focus_mode` (`Control.FOCUS_NONE`, `FOCUS_CLICK`, `FOCUS_ALL`, default ALL), `grab_focus()`, `release_focus()`, `has_focus()`, `get_focus_control()` and `focus_entered`/`focus_exited`. `get_focus_control()` returns the current native endpoint, or null outside the running tree/editor. Use it to author explicit native focus paths when needed; never hardcode its internal name. A two-pixel light-blue inset border marks actual focus, including pointer/programmatic focus.

A disabled target loses focus immediately. Hiding/unmounting/reparenting follows native GUI lifetime: pending activation is canceled, old endpoints are removed, reentry creates one new endpoint. Moving keyed retained Nodes in their native parent preserves identity/focus. Programmatic value changes notify; reconciliation suppresses automatic writeback through the mounted binding guard. Changing Toggle with completed keyboard activation uses the existing bool binding path, with one user edit.

## Traversal and event phases

Each existing Entry participates in one shared weak registry per Viewport. It retains no current-focused model or cached focus graph. Tab builds eligible native endpoints/Controls in **actual SceneTree order**, joins native GUI roots separated by Node2D, wraps, and Shift-Tab reverses. Nested Entries deduplicate their descendants. Click-only endpoints are skipped by Tab but can receive pointer/programmatic focus. Current native `focus_next`/`focus_previous` paths take priority if their target is eligible; no authored paths are rewritten. Controls outside participating Entries and other Viewports retain Godot's own behavior. Embedded Viewports retain Godot's native rules for acquiring GUI focus; the registry does not promise simultaneous OS keyboard ownership.

Eligibility requires a live, processable, visible target, permitted focus mode, positive arranged rectangle and a nonsingular canvas transform. Disabled native BaseButtons are skipped. A target must intersect the viewport and every native ancestor clip with positive area; fully clipped targets cannot acquire Estragon focus or be reached by shared Tab. Partly clipped controls are eligible at their actual visible rectangle. Scrolling a focused rectangle fully out of its clip releases focus on the event-driven refresh. This foundation **skips clipped targets rather than automatically scrolling them into view**. Native scrollbars remain normal native focusable Controls. Margins are not hit/focus rectangles; border-box geometry and current canvas transforms remain authoritative.

- Native `_input` remains available to application/platform handlers first. Entries consume shared Tab/Shift-Tab only for their participating native GUI owner (or to seed focus when none exists); key echoes do not repeat traversal.
- Godot GUI gets first refusal for primary-pointer events; existing inherited wheel/scroll ownership is unchanged. Estragon's existing weak geometric picker now runs in `_unhandled_input`. An overlapping native Control therefore wins rather than also activating a Node2D button. Among Estragon entries, one shared picker uses native CanvasLayer, inherited Z and tree order to select the winning entry; one existing pointer router owns capture/release. Disabled buttons continue to occlude lower custom targets. Existing native Control clipping/capture guards remain in place.
- A focused Estragon endpoint handles `ui_accept` key press/echo/release in `_gui_input`: press shows held state, echoes are quiet, matching release activates once. `ui_cancel` cancels a hold without activation; focus loss, disable/removal and Window focus loss also cancel. A key started elsewhere cannot activate this target on release. Mouse activation and keyboard activation both feed the same native `pressed` signal.
- Native Controls retain their own GUI processing. Native BaseButton can activate Enter yet leave it unhandled; Entry's `_shortcut_input` consumes that accept **after GUI processing**, before game unhandled-key handlers. It neither forwards nor re-emits an event. Accepting the native `gui_input` signal earlier would suppress the native activation and is deliberately avoided.
- Other keys follow native dispatch. Applications should accept UI input in the appropriate GUI phase and put game fallbacks in unhandled handlers. Raw `_input` handlers intentionally run before GUI ownership and can intercept events. Native LineEdit may leave key releases/unrecognized keys unhandled; this layer does not claim to swallow every native text event.

Tree changes and scroll geometry enqueue a coalesced eligibility check; direct custom disable/layout changes validate immediately. The registry holds weak Entries and disconnects its SceneTree subscription when the last Entry exits. No per-frame processing, second UI tree, additional reconciler/scheduler, authored metadata or helper layout participant is introduced. Native disabled/focus behavior remains native for foreign Controls; shared traversal skips disabled targets and revalidates at the next event. The framework does not poll arbitrary foreign property assignments.

## Text editing / IME decision and prototype

UI-03 completes the production [Input](INPUT.md) using this selected native editing path, including local skin, String model authority, retained caret/selection, border-box hit testing and pack/reload. The prototype and original comparison below remain UI-01 evidence; actual OS composition remains untested.

[Focus.gogo](../examples/focus/Focus.gogo) mixes Estragon Button/Toggle/Checkbox/disabled Button, Godot Button, and [TextDelegate.gd](../examples/focus/TextDelegate.gd), a deliberately limited Node2D host of a **real visible LineEdit**. Its internal owner-null LineEdit receives the host's allocated rect and inherits scene ancestry; native drawing, caret, selection, clipboard, editing keys, Unicode, submission and platform IME remain Godot-owned. It is **not catalogued as Input**, not a hidden offscreen text buffer, and offers no production String binding or completed Estragon input styling/validation API. Editor mode creates no runtime delegates.

| Approach | Native proof / responsibilities | Decision |
| --- | --- | --- |
| Native LineEdit under the real Node2D host | Actual text key, select-all and clipboard events; text/caret/selection/focus retained through Gogo rerender; shared traversal. Godot supplies OS IME/candidate positioning in the real native rect. | Use this platform editing path for UI-03, retaining a native endpoint in the actual clipped scene ancestry. UI-03 must finish presentation, model ownership, API and editing acceptance. |
| Fully custom drawing and raw key-to-string editing | The bounded runtime prototype can append Unicode but has no native selection/clipboard/IME contract; native GUI-consumed editing does not also reach its raw handler. A full implementation would have to add editing state, shaping/graphemes, caret/selection, undo/clipboard and DisplayServer IME lifecycle/candidate positioning itself. | Do not implement a second text editor for this foundation. Custom drawing can be considered separately only with a concrete native editing/delegation contract. |

The approved Linux engines exercise native editing and report `DisplayServer.FEATURE_IME`/backend. **Actual OS IME composition/candidate interaction is UNTESTED under Xvfb**; synthetic Unicode is not composition proof. Native LineEdit remains responsible for those platform services. Mobile/virtual-keyboard, accessibility, multiline input and custom text rendering are outside this issue.

Runtime endpoints have no scene owner and do not serialize. Persistent authored native Controls retain their original owners, focus paths and ancestry. Packed authored Node2D Buttons recreate one endpoint on mount; packed Gogo hosts recreate their transient output through the existing manager. The prototype deliberately starts again from authored `initial_text` after a new mount; it does not promise persistence of unsaved edits or a production model binding. UI-03 must define those value semantics.

## Validation

`tools/check-focus.ts` directly installs one immutable Yarn development payload, runs mixed native runtime and retained Gogo game checks, then real isolated editor current/main invalid-source rollback/repair/Play and restart. Tests exercise actual platform input dispatch (`Input.parse_input_event`), not direct calls to focus/key handlers. Godot4.0 `Viewport.push_input` does not itself deliver the unhandled phase; platform dispatch covers both engine paths without adding a production compatibility layer. Exact commands, source/package/engine provenance and rendered captures belong in the committed evidence and live issue/PR. Manual interactive smoke and actual OS IME composition are reported separately. Only official Linux4.0.4/pinned4.7.0 are freshly tested; routine CI remains ≤60 seconds.

[Paired native evidence](evidence/UI01_FOCUS_KEYBOARD.md) records exact source/engine/package qualification, captures, regressions and retained development failures.
